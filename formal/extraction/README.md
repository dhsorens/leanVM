# Rust to Lean extraction

Stage 1 of the [verification roadmap](../../VERIFICATION.md): the Rust crates are translated to Lean by [hax](https://hax.cryspen.com/)'s Lean backend (Charon, then Aeneas), each translation is committed beside the crate it comes from, and CI keeps it in step with the Rust. Nothing here is proved yet; what is checked is that every extraction is current and typechecks. What the extractions leave out, and why, is in [LIMITATIONS.md](LIMITATIONS.md).

## Layout

```
hax.toml                                  pins charon, aeneas, the Lean toolchain and the hax Lean library
crates/<crate>/hax.toml                   the crate's scenario: what is extracted, what is left opaque and why
crates/<crate>/proofs/<scenario>/
  patches/pre/NN-*.patch                  Rust rewrites, applied only while extracting
  patches/pre/tests                       optional: the tests that pin what the patches touch
  patches/post/NN-*.patch                 rewrites of the generated Lean (a last resort)
  lean/                                   the Lean package hax scaffolds, e.g. `Verifier`
    <Pkg>/Extraction/                     generated: hax rewrites it on every extraction, never edit
    <Pkg>/Assumptions/                    the Rust items left opaque, as axioms, kept in step by wire.py
    <Pkg>/Verification/                   hand-written proofs (none yet)
formal/extraction/
  hax.sh                                  setup, extract, test, and run commands on the patched source
  wire.py                                 wires every package into this workspace (run by hax.sh)
  report.sh                               what each extraction takes on trust, as a table
  CoreModelsExt/                          models of standard-library items the hax Lean library lacks
  lakefile.toml, Extraction/              the workspace, generated by wire.py
```

A crate takes part by declaring a [proof scenario](https://github.com/cryspen/hax/blob/main/docs/manual/tools.md#proof-scenarios) in its `hax.toml`; `hax.sh extract` does the rest. The scenario's `opaque` list names the items extracted as signatures only, grouped by what stops them, so it is also the work left.

This directory is the one Lake workspace: it requires every package by path and `CoreModelsExt`, so Aeneas, the hax Lean library, Mathlib and ArkLib (with CompPoly, which it requires) resolve once, in `formal/extraction/.lake/packages`, which each package also points at when built alone. `lake build` here builds every extraction, each as its own root. A crate's extraction imports those of the crates it depends on, which declare the items it uses from them.

## Using it

```bash
formal/extraction/hax.sh setup                  # once: cargo-hax, charon, aeneas, charon's nightly
formal/extraction/hax.sh extract                # regenerate every extraction (-p <crate> for one)
cd formal/extraction && lake exe cache get && lake build
```

The extraction is of the portable code: `hax.sh` switches off the hardware features the crates dispatch on, so every `cfg(target_feature)` choice takes its fallback, and the result is the same on any host (CI regenerates it on x86-64 Linux and compares).

After changing an extracted crate, run `hax.sh extract` and commit what changes under `crates/<crate>/proofs`; CI fails otherwise. Most changes regenerate cleanly. The ones that need attention:

- **A patch no longer applies.** `hax.sh extract` names it. Refresh it: apply the patches before it (`git apply`), apply it with `git apply --reject` or redo its rewrite by hand on the new code, then write it back with `git diff crates/<crate>/src > <patch>` and revert the source (`git checkout crates/<crate>/src`).
- **Aeneas rejects new code.** Its errors are in `lean/aeneas-error.log`. Rewrite the construct in a patch (below), or add the item to the scenario's `opaque` list under the reason.
- **The opaque items change.** Nothing to do: `hax.sh extract` adds the new declarations to `Assumptions/` and drops the stale ones, keeping those already there as they are.
- **A missing standard-library model.** Lean reports an unknown `core.*` or `alloc.*` constant: model it in `CoreModelsExt`, as a definition where the Rust is short, as an `opaque` otherwise.

## Patches

A patch in `pre/` rewrites Rust the toolchain cannot translate into Rust it can, without changing what it computes: an iterator adapter whose closure takes a reference (`filter`, `copied`) becomes a fold or a loop, a mutable iterator becomes an indexed loop, a function-pointer field becomes a method. Patches are applied in name order for the length of `hax.sh extract` and reverted after, so the committed source never carries them. Generated Lean is never edited by hand: what cannot be fixed in the Rust or in `Assumptions/` goes in a `post/` patch, applied to the output of every extraction, which is preferred only over leaving the item opaque.

`hax.sh test` holds every patched crate to two checks, in CI: clippy is clean on the patched source, and the crate's tests pass on it (`cargo test -p <crate>`, or each line of its `patches/pre/tests`, such as the verifier's checks against real proofs). They run on the portable code paths, the ones the patches rewrite. `hax.sh patched <command>` runs any command on the patched source, which is also how to inspect it.

## What the extraction trusts

`report.sh` counts, per extraction, the definitions extracted, the Rust items left opaque, the bodies Aeneas could not translate (`sorry`), and the patches; CI prints it on every run. Between the Lean and the Rust that runs stand:

- **The toolchain.** Charon, Aeneas, and the hax Lean library's models of `core` and `alloc` are trusted to translate faithfully.
- **The assumptions.** Opaque items are axioms with no body; the models in `CoreModelsExt` are as good as their definitions, and its `opaque`s are assumptions too.
- **The patches.** The Lean describes the patched Rust; the tests are the evidence that it computes what the committed Rust does. Source spans in the generated files point into the patched source.
- **The portable paths.** The SIMD and other hardware-specific code the crates run on x86-64 and aarch64 is not extracted (stage 3 of the roadmap).
